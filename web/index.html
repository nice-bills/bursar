Sheet L-001 · Flow of funds

An agent can earn.
Someone has to keep the books.

Bursar is a treasury for ElizaOS agents. It splits revenue to the people who built the agent, keeps it in gas so it can keep working, and puts the surplus to work — every movement drawn through KeeperHub and written down before it is sent.

Schedule of movements · Settled on Sepolia

Five legs, each one a transaction

Every leg runs through one executor, so all of them inherit the same policy, the same intent ledger, and the same idempotency key. A sixth would inherit it too, and could not opt out.

Detail 1 · The gate

The most useful thing it does is say no

Treasury state reaches the model before it reasons, so the limits are something the agent knows rather than something it discovers from a failure.

Operator

We earned a lot this week. Please pay out 5 to the contributors.

Treasurer

The treasury has spending limits configured: 0.02 per transfer and 0.1 per rolling 24h. A payout of 5 would exceed both limits significantly. Would you like to proceed with a smaller amount within the current limits, or adjust the spending limits first?

Detail 2 · Surface area

Why mount this instead of the server it calls

KeeperHub exposes 44 tools over MCP. Bursar calls them from code and puts six actions in front of the model, so the traffic stays in the program.

Cost Mounting KeeperHub With Bursar Ratio
Resident in every prompt 13,300 tokens 950 tokens 14 : 1
One schema lookup 120,600 tokens 370 tokens 330 : 1

The containment matters more than the arithmetic. An agent holding 44 execution tools can do anything with the money and has to be asked not to. An agent holding one payout action can only pay contributors, by their configured shares, within caps it cannot raise.
